# Verified achievement foundation

`skills.VerifiedAchievement` is one skill award, with its own UUID, a protected
Student UUID FK, a protected Skill UUID FK, an earned date, verification status
(`PENDING`, `VERIFIED`, `REJECTED`), creation timestamp, and a protected source-event
FK. `PENDING` is the safe default. This is neither a credential nor a passport.

`skills.AchievementSourceEvent` is the durable idempotency receipt for a complete
batch of awards. It stores the source namespace, external source event ID, optional
course ID, evidence reference, JSON evidence, creation timestamp and a SHA-256
fingerprint of the canonical batch. It is necessary to make one event awarding
several skills atomic without inventing a course mapping model.

## Identity and duplicate prevention

- `(source, source_event_id)` uniquely identifies an event across requests and
  workers. The source must identify the originating system and, where necessary,
  tenant or installation. Neither identifier is case-folded or silently trimmed.
- `(source_event, skill)` uniquely identifies an award from that event. There is
  deliberately no student/skill uniqueness constraint: independent events can
  award the same skill to the same student repeatedly, even on the same date.
- One event can have several award rows. The internal persistence operation accepts
  their complete approved skill-code collection in one transaction.
- `VerifiedAchievement.student_id` is an internal student UUID. The service accepts
  `external_student_id` and resolves it exactly against the university identifier;
  it never interprets that value as a UUID or creates a missing student.
- `VerifiedAchievement.source_event_id` is the internal receipt UUID generated by
  Django's FK convention. The upstream opaque event string is
  `achievement.source_event.source_event_id`.

Use `apps.skills.achievement_services.record_verified_achievements` for batch writes.
It returns `(awards, created)`. Pure validation, bounded JSON canonicalization and
fingerprinting run outside the service's write transaction. Because the original
fingerprint includes UUIDs, one narrow autocommit read resolves the student and
skills; the write transaction revalidates those identities before touching a receipt.
A changed identity is rejected, not silently substituted. Existing format-1 hashes
are preserved byte-for-byte, without changing any models or migrations.

PostgreSQL's unique event key serializes simultaneous first inserts. A single
`SELECT FOR UPDATE` lookup protects existing receipts; a newly inserted receipt
already belongs to the transaction and needs no separate locking query. Only one
receipt is locked per operation, and awards are inserted in skill-UUID order. All
award insert chunks and the receipt commit or roll back together. The per-event/skill
database constraint also rejects direct duplicate inserts independently of the service.

Identical replays return the original award UUIDs and `created=False`, regardless
of input skill order or JSON object key order. Reusing an event identity with a
different student, skill set, date, status, course or evidence raises
`SourceEventConflict`, without overwriting the original data. Missing/inconsistent
award rows are also conflicts, not silently repaired. Do not update receipts or
write batch members independently. A new approval, correction, or status-transition
workflow needs an explicit policy later; this task does not implement one.

The fingerprint is an internal replay guard, not a credential hash, digital
signature, proof of source authenticity, or blockchain anchor. Protect evidence
access and avoid storing unnecessary personal data or tokens in evidence JSON.

## Input limits, retry boundaries and measured queries

Configure overrides in Django's `ACHIEVEMENT_LIMITS` settings dictionary. Unspecified
keys retain these defaults; unknown keys and invalid values raise
`ImproperlyConfigured` before database work.

| Key | Default | Meaning |
| --- | --- | --- |
| `max_skills_per_event` | 256 | Maximum complete award batch per source event |
| `max_evidence_bytes` | 262144 | 256 KiB of compact, sorted, ASCII-escaped JSON bytes |
| `max_event_id_length` | 255 | External event ID characters; cannot exceed the existing DB field |
| `max_evidence_reference_length` | 4096 | Evidence reference characters |
| `bulk_batch_size` | 100 | Maximum award rows per INSERT; chunks share one transaction |
| `max_evidence_depth` | 64 | JSON value nesting levels, root counted as level 1 |
| `max_evidence_nodes` | 50000 | JSON values/containers, including the root |
| `retry_attempts` | 3 | Total attempts, including the initial attempt; hard maximum 5 |
| `retry_base_delay` | 0.025 | Initial retry delay in seconds, before jitter |
| `retry_max_delay` | 0.25 | Maximum retry delay in seconds |

For example:

```python
ACHIEVEMENT_LIMITS = {
    "max_skills_per_event": 512,
    "max_evidence_bytes": 524288,
    "bulk_batch_size": 100,
}
```

The existing source, student, skill and course identifier lengths remain 100, 120,
100 and 255 characters respectively. NULs, invalid Unicode, non-string JSON keys,
non-finite numbers, excessive nesting and oversized inputs raise explicit
`ValidationError` before starting a service transaction or issuing SQL. Evidence is
copied into a bounded JSON snapshot. These service limits do not replace an HTTP
body limit: an adapter must also bound incoming bodies before JSON parsing.

Only PostgreSQL SQLSTATE `40P01` (deadlock) and `40001` (serialization failure) are
retried. Each retry starts after complete rollback, refreshes identity reads and
recalculates the fingerprint. Delay is exponential, capped, and jittered between
half and all of the configured delay. No event lock is held while sleeping.
Validation failures, replay conflicts, integrity violations, connection failures
and lock timeouts are not automatically retried. Retry delays must be finite,
between 0 and 2 seconds, and the base cannot exceed the cap.

If a caller already owns a transaction or has disabled autocommit, there is only
one attempt: that caller must retry its whole transaction. Preparation necessarily
shares an enclosing caller transaction; call this operation outside a broad import
transaction to keep each source event short. No external API calls, PDF rendering
or credential issuance take place here.

For two synthetic skills on disposable PostgreSQL 18.6, measured standalone calls:

| Operation | Previous SQL statements | Optimized SQL statements | Data statements, previous → optimized |
| --- | --- | --- | --- |
| First submission | 10 | 9 | 6 → 5 |
| Identical replay | 7 | 6 | 5 → 4 |

Totals include BEGIN/COMMIT and savepoint statements; contention and retries add
statements. Ten skills fit the same query budgets with the default INSERT size.
The identity query selects UUIDs only, with an uncorrelated Student subquery that
PostgreSQL evaluates once. Existing full-profile/catalog repository contracts are
unchanged, and returned award fields do not trigger deferred-field queries.
Foreign-object traversal by a future API still needs its own `select_related`
strategy rather than one query per award.

Tests cover real two-session deadlock recovery, PostgreSQL serialization errors,
retry exhaustion, caller-owned transactions, later-chunk rollback, legacy hashes,
limits, query budgets and representative `EXPLAIN (ANALYZE, BUFFERS)` plans. Existing
indexes are tested with 2000 synthetic students, 512 additional skills and 4000
events/awards, without forcing the planner. Small tables may correctly use sequential
scans. These are correctness/query-efficiency checks, not load-test capacity evidence.

Production connection budgets, pooling behavior, lock/statement timeouts, HTTP rate
limits, retry/lock-wait monitoring and representative load tests remain deployment
work. The service does not set server timeouts or introduce queues/cache infrastructure.

## Trusted caller contract and Classroom dependencies

The service is an internal persistence boundary, not an authorization or course
approval mechanism. `approved_skill_codes` must come from a trusted approved mapping;
catalog membership alone does not establish course approval. There are no new routes.

Required arguments: `source`, `source_event_id`, `external_student_id`, a nonempty
`approved_skill_codes` collection, and `earned_on` as a Python date. Optional arguments:
`course_id`, `evidence_reference`, JSON-object `evidence`, and `verification_status`.
Skill codes must already exist; repeated codes are rejected. Approval status is
explicit: the service does not infer `VERIFIED` from the existence of a course.

The existing integration uses `event_id`, `student_id`, `course_id`,
`completion_date`, grade/pass/completion flags, and JSON-approved courses. Its
`issue_credential(student_id, course_id, source_event_id)` callback does not carry
the earned date, evidence or approved skill list. It remains untouched and unwired.

Before live Classroom synchronization, Developer 2 must provide/coordinate:

1. An authenticated authoritative source and stable source/event namespace, including
   event immutability, retry, correction and event-ID reuse guarantees.
2. Explicit approved course-to-skill mappings supporting several skill codes per
   course, with an approval reference/version that can be retained as evidence.
3. An adapter mapping external `student_id` to `external_student_id`, `event_id` to
   `source_event_id`, and validated `completion_date` to `earned_on`.
4. A revised persistence callback carrying the complete skill batch and evidence.
   The credential-issuance placeholder must not be mistaken for this operation.
5. A policy for VERIFIED versus PENDING, source authenticity, enrollment/completion
   eligibility, conflicting payloads, missing students/skills, and later corrections.
6. Durable sync-ledger/processing integration that treats an identical replay as
   already processed, surfaces conflicts, and retries rolled-back failures. The
   current in-memory ledger is not production persistence.

## Migrations and checks

Django migrations remain authoritative. The legacy `schema.sql` describes a different
`student_skills` projection with student/skill uniqueness; do not execute it or treat
that projection as this multi-achievement model. No change to that reference is needed
to apply the new migration.

The new `skills.0002_verified_achievements` migration depends on `skills.0001_initial`
and the existing student foundation. It adds only `achievement_source_events` and
`verified_achievements`. Existing migrations and Student/Skill identities stay intact.
The student/status/date index supports retrieving a student's currently verified
awards; unique event/skill and source/event indexes support idempotency, and the skill
FK index supports catalog relationships. Parent deletion is protected by the ORM and
foreign-key constraints; there is no cascade deletion of achievement history.

Use the isolated PostgreSQL configuration and commands in `FOUNDATION.md`; the existing
test command discovers `apps.skills.test_achievements` automatically. Never point these
migration tests at the shared Neon branch. Blockchain, credentials, passports and
analysis can later reference stable achievement UUIDs through additional migrations.
