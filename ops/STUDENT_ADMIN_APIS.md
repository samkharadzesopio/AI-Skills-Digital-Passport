# Student and Administrator REST APIs

All interfaces use the existing Django models, PostgreSQL database, account sessions,
credential services, and passport services. No frontend or shared Neon database was changed.
Base: `origin/integration` at `f8057c556822683e8baa2a7e3835be45876b958a` (freshly fetched).

## Authentication and permissions

Use existing `/api/accounts/` login/logout/CSRF flows and session cookies. Unsafe
requests require the existing CSRF token. No tokens or alternative login mechanism
were added. Every response from the private views has `Cache-Control: no-store`.

Student access requires an active, email-verified STUDENT account linked to an active
canonical Student with matching approved university email. Identity comes only from
the account. Client-supplied student IDs never select another student's data.
Credential and version detail queries are scoped to that identity and also invoke
the existing object permission classes. Foreign/missing UUID objects return 404.

Administrators must satisfy `has_admin_permission`: active, email verified, ADMIN
role, staff, non-superuser, and the exact Django permission below. Each write attempt
and outcome uses `AuditedAPIView` / `SecurityAudit`; credential lifecycle events and
refresh outbox records remain managed by the existing services.

| Operation | Required permission |
|---|---|
| All administrative GET routes | `accounts.view_student_records` |
| Student POST/PATCH | `accounts.manage_student_accounts` |
| Credential issue | `accounts.manage_credentials` |
| Credential revoke | `accounts.revoke_credentials` |

## Endpoints

All paths below start with `/api/`. Object `{id}` parameters are internal UUIDs,
not university IDs or public references. Public references remain explicit response fields.
All collection responses use `{count, next, previous, results}`. `page` defaults to 1;
`page_size` defaults to 25 and is capped at 100. Ordering is deterministic.

| Method | Path | Response / parameters |
|---|---|---|
| GET | `student/dashboard/` | Dashboard described below |
| GET | `student/skills/` | Recognized skill collection, with latest 100 verified achievements per skill |
| GET | `student/achievements/` | Verified achievement collection; optional `skill_id` UUID |
| GET | `student/credentials/` | Own credential collection |
| GET | `student/credentials/{id}/` | Own credential |
| GET | `student/passport/` | Own passport, or `{"passport": null}` when absent |
| GET | `student/passport/versions/` | Own issued version collection; empty when no passport |
| GET | `student/passport/versions/{id}/` | Own issued snapshot |
| GET | `admin/students/` | Student collection; `search` (max 150 chars, name/email/external ID), exact `program`, `education_level`, `student_status` |
| POST | `admin/students/` | Create student; 201 |
| GET | `admin/students/{id}/` | Student dashboard/overview, same shape as student dashboard |
| PATCH | `admin/students/{id}/` | Approved profile update; 200 |
| GET | `admin/credentials/` | Credential collection; `student_id` UUID, `status` |
| GET | `admin/credentials/{id}/` | Credential |
| POST | `admin/credentials/issue/` | Idempotent service issuance; 200 for initial request and replay |

| GET | `admin/passports/` | Passport collection; optional `student_id` UUID |

The preexisting profile route `/api/students/students/{external_student_id}/` and
public verification routes are retained unchanged. Dashboard recent lists contain
at most five items; complete student histories use the paginated routes.

## Request contracts

Student creation requires `external_student_id`, `first_name`, `last_name`, `email`,
`program`, `education_level`, `student_status`. IDs are generated by the model.
Model constraints and serializer validation reject duplicates/blank values.
PATCH permits only `program`, `education_level`, `student_status`.
University identities (`external_student_id`, email, first/last name) cannot change
through PATCH. Account linking, UUID assignment, and unknown input fields are rejected.
This API never creates or links an account; use the established invitation workflow.

Issue body:

```json
{"idempotency_key":"institution-event-123","achievement_ids":["<uuid>"],"expires_at":null}
```

`achievement_ids` must contain 1–256 unique UUIDs (the service may apply a stricter
configured maximum), all verified and belonging to one student. `expires_at` is
optional, must be after issuance when supplied. Issuance time is server controlled.
Issuer is always `BTU-UNIVERSITY`; issuer override is rejected. A trusted BTU issuer
must already be provisioned through the established administrative workflow.
Reusing a key with different parameters returns 409. Revocation body is
`{"reason":"Institutional reason"}` (nonblank, at most 2,000 characters).

## Response contracts

- Student: `id`, `external_student_id`, `first_name`, `last_name`, `email`, `program`,
  `education_level`, `student_status`.
- Skill: `id`, `skill_code`, `skill_name`, `category`, `subcategory`,
  `competency_level` (existing stamp type: FOCUSED/APPLIED/ADVANCED), `description`.
  Recognized skill rows also contain `achievements` and `achievements_limit: 100`.
  Use `student/achievements/?skill_id=...` for the complete paginated history.
- Achievement: `id`, nested `skill`, `course_reference` (empty if unavailable),
  `earned_on`, `verification_status`. The verified record/course reference supports
  the award; arbitrary ingestion evidence JSON, internal source IDs, and evidence
  URLs are deliberately not exposed without an established safe evidence schema.
- Credential: `id`, `public_reference`, `student_id`, `issuer_reference`, `issuer_name`,
  `issued_at`, `expires_at`, stored `status`, computed `validity_status`, `revoked_at`,
  nested `achievements` (including associated skills). No idempotency fingerprint,
  actor identity, ingestion payload, or internal audit data is exposed.
- Version: `id`, `public_reference`, `version_number`, `status`, `issued_at`,
  `created_at`, frozen `skills`, frozen `credentials`. Skill snapshots contain
  `skill_id`, code, name, category, subcategory, description, `stamp_type`.
  Credential snapshots contain public reference, issuer reference/name, issue/expiry dates.
- Passport: `id`, `public_reference`, `student_id`, `status`, timestamps,
  `latest_version` (nested issued snapshot or null). Status is ISSUED or NOT_ISSUED;
  it denotes publication state, not a guarantee every historical credential is current.
- Dashboard: `profile`, `recognized_skills`, `skills_by_category`,
  `skills_by_subcategory`, `verified_achievements`, `credentials` counts,
  `recent_achievements`, `recent_credentials`, `passport` (null when absent).
- Statistics: `students`, `credentials` counts, `passports`, `recognized_skills`,
  `skills_by_category`, `skills_by_subcategory`, `verified_achievements`.

Counts use `{total, valid, expired, revoked, invalid}`. `total` counts all credential
rows, including revoked and expired ones. Validity follows `verification_status_at`:
revoked takes precedence; future issuance is INVALID; expiration at or before now
is EXPIRED; remaining issued credentials are VALID. Admin status filtering accepts
ISSUED (stored lifecycle state), VALID, EXPIRED, REVOKED, INVALID.

Recognized skills are distinct catalog skills with VERIFIED awards, not inferred
scores. University recognized skill statistics count distinct skills across students,
not student-skill pairs; verified achievement totals count awards. Category and
subcategory distributions are arrays such as `[{"subcategory":"Reasoning","count":1}]`.
Empty subcategories group under `""`; no hierarchy is inferred or backfilled.
Counts/filtering/grouping run in PostgreSQL; relations are eagerly loaded.

## Errors

400: field validation errors (including invalid filter UUID/status, protected fields,
model constraints); 403: unauthenticated/unauthorized/CSRF rejection under existing
session authentication; 404: unknown/foreign objects, malformed path UUID, invalid
page; 405: unsupported method; 409: idempotency conflict; 503: required institutional
service configuration missing. Bodies use DRF field errors or `{"detail":"..."}`.
Duplicate identity races are caught transactionally and reported as safe 400 errors.

## Domain reuse and migrations

`issue_credential`, `revoke_credential`, `verification_status_at`, existing account
identity/permission functions, audit views, immutable snapshot models, and durable
refresh processing remain authoritative. A preexisting immediate-refresh callback
passed a positional argument to a keyword-only processor; it now passes `refresh_id=`.
The worker/outbox architecture is unchanged.

Additive migrations:

- `skills/0003_skill_subcategory`: optional non-null text (150 chars), default empty.
- `passports/0006_snapshot_subcategory`: corresponding frozen field and replacement
  snapshot guard function enforcing equality with the source catalog on insertion.
  Reverse SQL restores the prior guard before dropping the snapshot field.

Existing issued rows, hashes, dates, and associations are never rewritten. Old
snapshots receive an empty subcategory because historical classification is unknown.
New snapshots freeze the catalog value and include it in the content hash. PDF
context and rendering use the frozen field; renderer version/fingerprint advances
so new document generations cannot reuse a prior renderer's artifact. Existing
stored PDFs remain unchanged. Review/apply these migrations only during the later
coordinated integration phase; no shared Neon migration was performed.

No competing passport generation endpoint was added. Issuance/revocation invoke
the existing refresh/outbox path; the existing worker remains necessary for retry
and expiry processing. Historical snapshots remain historical even after revocation.
Public verification retains its configured trusted-issuer allowlist and privacy contract.

## Verification and integration

See `STUDENT_ADMIN_REPORT.md` for actual commands, results, and final file inventory.
The standard `ops/test_backend.sh` now includes `apps.api`. Tests use the existing
loopback-only PostgreSQL settings, never `config.settings` or `.env`/DATABASE_URL.

No real concurrency/load benchmark was performed; query-count checks establish
bounded relation loading, not 5,000 concurrent-user capacity. Before frontend
integration, agree on institution-approved subcategory values, review the profile
update whitelist, apply migrations in an isolated staging copy, and run joint
regression tests. The next backend phase should exercise realistic data volumes,
load and worker recovery in staging, then finalize evidence exposure policy.
